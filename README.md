# Ecom Connector

Standalone, multi-client SaaS product that owns the full lifecycle of
connecting a tenant's Amazon or Flipkart seller account via OAuth:
registration, OAuth handshake, encrypted token storage/refresh, order
(and payments/returns) fetch, reauthorization, disconnect.

Consuming client applications (Speedecom is the first, not the only one)
never talk to Amazon/Flipkart directly and never store a marketplace
credential — they call the Connector's own API instead.

---

## 1. Setup

**Prerequisites:** Node version per `.nvmrc`, a running MongoDB and Redis, `npm install`.

**Environment:** copy `.env.example` → `.env` and fill it in. Three groups of variables:

| Group | Vars | Notes |
|---|---|---|
| Connector core | `PORT`, `NODE_ENV`, `TRUST_PROXY`, `MONGO_URI`, `REDIS_URL` | Standard service config |
| Connector secrets | `MASTER_ENCRYPTION_KEY`, `OAUTH_STATE_SECRET` | Generate once, 64-char hex for the key (32 bytes, AES-256-GCM). Keep stable — rotating `MASTER_ENCRYPTION_KEY` makes every stored refresh token undecryptable |
| Marketplace app credentials | `AMAZON_*`, `AWS_*`, `FLIPKART_*` | One shared set for the whole Connector, from registering the Connector itself with each marketplace — never per-client, never stored in Mongo |

Per-client credentials (`client_id`/`client_secret`) are **not** env config — see §5.

**Registering the Connector with Amazon:** Seller Central → Apps & Services → Develop Apps.
- **Private** app — self-authorize your own seller account in Seller Central; you get a refresh token directly, no redirect involved.
- **Public / Solution Provider** app — required for onboarding other sellers; uses a real consent-screen redirect and goes through Amazon's app review. Set `AMAZON_DRAFT_MODE=true` to test the real consent flow before that review completes (Amazon requires `version=beta` on the authorization URL for an unreviewed app); flip to `false` once approved.
- Either type needs: `application_id`, LWA `client_id`/`client_secret`, and a redirect URI registered with Amazon that exactly matches `AMAZON_OAUTH_REDIRECT_URI` (one shared `/oauth/callback` path, not one per marketplace).
- `AMAZON_AUTHORIZATION_BASE_URL` and `AMAZON_SP_API_BASE_URL` are region-specific — they must match the seller's actual marketplace region (e.g. `sellercentral.amazon.in` + `sellingpartnerapi-eu.amazon.com` for India), not just the account used to register the app.
- `AWS_*` vars back an SP-API SigV4 signature the Connector computes on every call; a real IAM user/role is only needed if that signature must actually be checked by something other than Amazon's SP-API (which currently ignores it — see §9).

**Registering the Connector with Flipkart:** Seller Dashboard → Manage Profile → Developer Access. Self-Access (own store) or API Partner (~72h verification) — same redirect-URI registration pattern as Amazon.

**Public redirect URI for local development:** neither marketplace accepts `localhost` as a redirect URI. Use `ngrok http <PORT>` (claim ngrok's one free static domain so it survives restarts), and register `https://<domain>/oauth/callback` with both marketplaces and in `.env`. A real deployment needs the same thing — your own stable public domain instead of ngrok.

**Starting the server:**
```
npm run dev      # nodemon, local development
npm start        # plain node, production
```

**Onboarding a client application:**
```
node scripts/createClient.js --name "Speedecom" --return-url "https://speedecom.example.com/marketplaces/callback"
```
Prints `client_id`/`client_secret` once — store immediately, it is never shown again.

## 2. Core concepts

**Identifiers:**

| ID | Answers | Generated by |
|---|---|---|
| `client_id` / `client_secret` | Who is calling the Connector? | Connector, once per client, via `scripts/createClient.js` |
| `tenant_id` | Which of that client's customers? | The client — reused as-is via `sync_tenants` |
| `marketplace_connection_id` | Which specific seller account? | The client — reused as-is via `connect` |

Both `tenant_id` and `marketplace_connection_id` are opaque strings with no
assumed format; uniqueness is scoped by `client_id` first, so any ID scheme
(UUID, slug, numeric) works with no schema change.

**Credential pairs — three, independent:**

| Pair | Scope | Stored | Sent as |
|---|---|---|---|
| Client ↔ Connector | One per client | `Client.client_secret_hash` (Argon2id) | `x-client-id` / `x-client-secret` headers |
| Connector ↔ Amazon/Flipkart | One per marketplace, shared by every client | Env config, never in Mongo | Used internally only |
| Connector ↔ AWS (Amazon only) | Connector-wide | Env config + Redis-cached STS temp creds | SigV4 signature on SP-API calls |

**Connection lifecycle:**

```
PENDING → ACTIVE              OAuth callback succeeds
ACTIVE → REAUTH_REQUIRED      token refresh fails (revoked/expired grant)
REAUTH_REQUIRED → ACTIVE      connect() called again (upsert)
PENDING → DISCONNECTED        abandoned-PENDING sweep (30 min timeout)
ACTIVE/REAUTH_REQUIRED
   → DISCONNECTED             explicit disconnect, tenant deletion, client revocation
```
`connect()` always upserts — there is no separate reconnect endpoint; it works from any current status.

**Sync semantics:**

| Level | Payload | Direction | Frequency |
|---|---|---|---|
| Client | none — Connector generates the pair | Connector → Client | Once, at onboarding |
| Tenant | `tenant_id`, `status: active\|inactive`, `label?` | Client → Connector, `sync_tenants` | Bulk, re-callable anytime |
| Connection | `marketplace`, `marketplace_connection_id`, `label?` | Client → Connector, `connect` | One at a time |

- Push-only: the Connector never calls back into a client's systems.
- Omission ≠ deactivation — a tenant left out of a `sync_tenants` call is untouched; deactivation requires an explicit `status: "inactive"` entry.
- No order data, billing, or user/permission info ever crosses the client boundary in the other direction.

## 3. API reference

Base path `/v1`. Every request except the OAuth callback requires
`x-client-id` / `x-client-secret` headers.

### `POST /v1/actions`

Body's `action` field selects the operation:

**`sync_tenants`**
```json
{ "action": "sync_tenants", "tenants": [{ "tenant_id": "T-1", "status": "active", "label": "Acme Co" }] }
→ { "tenants": [...] }
```

**`connect`** — starts (or restarts) the OAuth flow for one seller account.
```json
{ "action": "connect", "tenant_id": "T-1", "marketplace": "amazon", "marketplace_connection_id": "SELLER-1", "label": "Primary Store" }
→ { "authorization_url": "https://sellercentral.amazon.in/apps/authorize/consent?..." }
```
Redirect the seller's browser to `authorization_url`.

**`disconnect`**
```json
{ "action": "disconnect", "tenant_id": "T-1", "marketplace": "amazon", "marketplace_connection_id": "SELLER-1" }
→ { "status": "disconnected" }
```
Idempotent — disconnecting an already-disconnected connection is a `200` no-op.

**`delete_tenant`**
```json
{ "action": "delete_tenant", "tenant_id": "T-1" }
→ { "tenant_id": "T-1", "deleted_connections": 2 }
```
Soft-deletes the tenant and disconnects every connection under it.

**`fetch_orders`**
```json
{ "action": "fetch_orders", "tenant_id": "T-1", "marketplace_connection_id": "SELLER-1", "from": "2026-01-01T00:00:00Z", "to": "2026-01-31T00:00:00Z" }
→ { "orders": [{ "order_id": "...", "marketplace": "amazon", "status": "...", "order_date": "...", "total_amount": ..., "currency": "...", "raw": { ... } }] }
```
Paginates internally (capped at 20 pages per call). `raw` carries the
untouched marketplace response object — this is where Amazon-specific
fields like `IsBusinessOrder`/`BuyerInfo`/`BuyerTaxInfo` (B2B/B2C data)
are found; no separate action is needed for them.

**`fetch_data`** — Payments and Returns, under one action with a `data_type` discriminator.
```json
{ "action": "fetch_data", "tenant_id": "T-1", "marketplace_connection_id": "SELLER-1", "data_type": "payments", "from": "...", "to": "..." }
→ { "transactions": [...] }   // Amazon only

{ "action": "fetch_data", "tenant_id": "T-1", "marketplace_connection_id": "SELLER-1", "data_type": "returns", "from": "...", "to": "..." }
→ { "returns": [...] }        // Amazon or Flipkart
```
Range caps: 180 days for `payments`, 60 days for Amazon `returns`. `to`
must not be before `from`.

### `GET /v1/query`

**`connection_status`**
```
GET /v1/query?resource=connection_status&tenant_id=T-1&marketplace_connection_id=SELLER-1
→ { "status": "active", "last_connected_at": "...", "last_error": null }
```

### `GET /oauth/callback`

Public, unauthenticated — this is where Amazon/Flipkart redirect after the
seller authorizes. Never called directly by a client; protected by a
signed, single-use `state` parameter instead of client credentials.

### Error codes

| Code | HTTP | Meaning |
|---|---|---|
| `UNAUTHORIZED` | 401 | Missing/wrong client credentials |
| `FORBIDDEN` | 403 | Client `status: revoked` |
| `RATE_LIMITED` | 429 | Token bucket exhausted |
| `VALIDATION_ERROR` | 400 | Request body/query failed schema validation |
| `UNKNOWN_ACTION` / `UNKNOWN_RESOURCE` | 400 | Unrecognized `action`/`resource` value |
| `INVALID_OAUTH_STATE` | 400 | Callback `state` invalid, expired, or replayed |
| `CONNECTION_NOT_FOUND` / `TENANT_NOT_FOUND` | 404 | No matching document |
| `CONNECTION_PENDING` | 409 | Data requested before the OAuth flow finished |
| `REAUTH_REQUIRED` | 409 | Seller needs to `connect()` again (token revoked/expired) |
| `PROVIDER_UNAVAILABLE` | 503 | Transient marketplace/network error — connection status untouched, safe to retry |
| `CONNECTION_DISCONNECTED` | 409 | Data requested on a torn-down connection |
| `MARKETPLACE_IDS_NOT_POPULATED` | 409 | Amazon connection needs to reconnect to populate `marketplace_ids` |
| `INVALID_DATE_RANGE` | 400 | `to` before `from`, range exceeds the marketplace's max window, or `from` too recent |
| `DATA_TYPE_NOT_SUPPORTED` | 400 | e.g. `fetch_data` payments on a Flipkart connection |
| `AMBIGUOUS_CONNECTION` | 500 | `marketplace_connection_id` matched more than one connection |
| `ROUTE_NOT_FOUND` | 404 | No route matched |
| `INTERNAL_ERROR` | 500 | Unhandled server error |

## 4. Client integration guide

1. Store `client_id`/`client_secret`/`CONNECTOR_BASE_URL` in your own config — send them only as `x-client-id`/`x-client-secret` headers, every call.
2. Call the Connector **server-to-server only**. There is no CORS layer — a browser `fetch()` with these headers is cross-origin and gets blocked by preflight.
3. Wrap the two endpoints in a thin client:
   ```js
   const client = axios.create({
       baseURL: process.env.CONNECTOR_BASE_URL,
       headers: {
           'x-client-id': process.env.CONNECTOR_CLIENT_ID,
           'x-client-secret': process.env.CONNECTOR_CLIENT_SECRET
       }
   });

   const connect = ({ tenant_id, marketplace, marketplace_connection_id, label }) =>
       client.post('/v1/actions', { action: 'connect', tenant_id, marketplace, marketplace_connection_id, label })
             .then((r) => r.data);
   // sync_tenants / disconnect / delete_tenant / fetch_orders / fetch_data: same shape.
   // connection_status: GET /v1/query?resource=connection_status&tenant_id=...&marketplace_connection_id=...
   ```
4. Call `sync_tenants` at least once before anything else for a given tenant — the Connector does not discover tenants on its own.
5. Implement the Connect redirect: call `connect()`, take the `authorization_url` it returns, and `res.redirect()` the seller's browser there.
6. Implement the landing page at the `default_return_url` given at client registration (fixed, not per-request — a per-request return URL would be an open-redirect vector). Don't trust the redirect's query params directly; call `connection_status` to confirm the real status before showing anything to the seller.
7. Own `marketplace_connection_id` values yourself — the Connector never generates or discovers these. Use your own merchant/seller ID field.
8. Keep a local table mapping `(tenant_id, marketplace, marketplace_connection_id)` → cached state (status, label). The Connector has no list-all endpoint; it is the system of record for *state*, your application is the system of record for what *exists*.
9. Handle `PROVIDER_UNAVAILABLE` (503) as retryable and `REAUTH_REQUIRED` (409) by prompting the seller to reconnect — these are the two states that mean different things despite both coming from a failed token refresh.

## 5. Security model

| Aspect | Mechanism |
|---|---|
| Refresh tokens | AES-256-GCM per field (`{data, iv, authTag}`) — tamper-evident |
| Client secrets | Argon2id hash; plaintext shown once at creation, never stored or logged again |
| OAuth CSRF | HMAC-signed `state`, 10-minute TTL, single-use (atomic Redis `GETDEL`) |
| Client auth | `x-client-id`/`x-client-secret` checked against the `Client` collection directly — no token-mint step; unknown-client and wrong-secret return identical timing and an identical 401 (no enumeration) |
| AWS SigV4 | Temp STS creds sign Amazon SP-API calls, never the raw long-lived IAM key |
| Public callback | `GET /oauth/callback` has no credential check — protected only by the signed `state` |

## 6. Rate limiting

Redis-backed token bucket (`rl:<name>:<identifier>`), atomic Lua script,
`429` + `Retry-After` header on block, fails open on Redis errors.

Two independent dimensions: `authAttempt` (keyed on IP + claimed
`client_id`, 20 pts/60s default) and `clientApi` (keyed on the
authenticated client, 60 pts/60s default).

## 7. Data model

```
Client
  _id, client_id, client_secret_hash, name, default_return_url,
  status: active|revoked, createdAt

Tenant
  _id, client_id (ref), tenant_id, label?,
  status: active|inactive, deletedAt: Date|null
  unique index: (client_id, tenant_id)

Connection
  _id, client_id (ref), tenant_id, marketplace: amazon|flipkart,
  marketplace_connection_id, status: pending|active|reauth_required|disconnected,
  encrypted_refresh_token: {data, iv, authTag}|null,
  marketplace_ids: [String]  — Amazon-only, populated post-OAuth; always [] for Flipkart
  label?, last_connected_at, last_error
  unique index: (client_id, tenant_id, marketplace)

Redis
  access_token:<client_id>:<tenant_id>:<marketplace_connection_id>  — TTL = token expiry minus safety margin
  oauth_state:<state>                                                — TTL ~10 min, single-use
  aws_sts_credentials                                                — Connector-wide
  rl:<name>:<identifier>                                             — rate-limit state
```

## 9. Marketplace-specific notes

**Amazon (SP-API):**
- Region-locked — `AMAZON_AUTHORIZATION_BASE_URL` and `AMAZON_SP_API_BASE_URL` must match the seller's actual marketplace region, not just wherever the app happens to be registered.
- `AMAZON_DRAFT_MODE=true` is required to test the consent flow on an app still pending Amazon's review; turn it off once approved.
- The OAuth callback param is `spapi_oauth_code` (plus an unsolicited `selling_partner_id`), not the standard `code` — handled transparently, no client-side change needed.
- SP-API currently ignores the AWS SigV4 signature on every request (LWA-only auth in practice) but the Connector still computes and sends one; `AWS_*` env vars can hold any syntactically valid values.
- Payments use the Finances API (`transactions`, `postedAfter`/`postedBefore`), capped at a 180-day window per call.
- Returns use `GET_XML_RETURNS_DATA_BY_RETURN_DATE`, which covers merchant-fulfilled (MFN) orders and needs only the "Inventory and Order Tracking" role — capped at a 60-day window per call. It does not cover FBA-fulfilled returns.
- B2B/B2C order data (`IsBusinessOrder`, `BuyerInfo`, `BuyerTaxInfo`) is already present in `fetch_orders`' `raw` field — no separate call.
- Amazon Advertising is a separate product from SP-API (its own OAuth app, scopes, and regional hosts) and is not implemented here.

**Flipkart:**
- Authorization requires `scope=Seller_Api`; token exchange uses HTTP Basic Auth with query-string params, not a POST body.
- Order search is `POST /sellers/v2/orders/search` with a nested JSON filter body; pagination follows the `nextPageURL` the response returns, not a computed offset.
- Returns: `GET /sellers/v2/returns`, paginated via a `nextUrl` field.
- Payments/settlement reports require both Partner-tier registration (~72h verification) and a separate paid commercial agreement with Flipkart — not implemented; `fetch_data` with `data_type: "payments"` on a Flipkart connection returns `DATA_TYPE_NOT_SUPPORTED`.
- "Flipkart Commerce Cloud" (their ads product) is not OAuth-based — it issues a static `X-AUTH-TOKEN` after a commercial onboarding process — and is not implemented here.
- Single domain, India-only — no region split like Amazon's.

**Meesho:** not implemented as an OAuth adapter. Meesho's partner API uses manually-issued credentials with a human-in-the-loop onboarding process, not a consent-screen redirect — a different `Connection` shape than the rest of this Connector. Speedecom's existing Meesho integration (browser automation) is separate and unrelated to this project.

## 10. Known limitations

- `fetch_orders` truncates silently past its 20-page-per-call budget — no `truncated` signal in the response.
- No per-order-item enrichment call — only the orders-list endpoint's own fields.
- `revokeToken` is a no-op on both adapters — neither Amazon nor Flipkart exposes a public revoke endpoint; disconnect only discards the Connector's own copy of the token.
- Client-level revocation cascade is provisional — revisit before a second real client depends on it.
- **A tenant can hold only one Amazon connection and one Flipkart connection at a time** — `connect()`'s upsert key is `(client, tenant_id, marketplace)`, not including `marketplace_connection_id`. Connecting a second seller account under the same tenant + marketplace overwrites the first. Supporting multiple seller accounts per tenant/marketplace needs a schema and migration change, not a same-pass patch.
- No automated test suite yet — `package.json` has `start`/`dev` only. Everything has been verified through direct, real API calls (real Amazon account, real MongoDB/Redis) and a passive OWASP ZAP baseline scan (0 findings across both public and authenticated routes), but there is no regression guard for future changes.
